0601 实验报告 ​

1、top ​

输入 top 可以观察系统进程。

占用 CPU 和内存（MEM）最多的是 gnome-s+，据资料，全称是 GNOME-shell，但不是我们说的 bash，应该是整个桌面环境的图形界面外壳。

我发现这个和 windows 任务管理器的每秒刷新不同，是 3s 一刷新。

我通过 k PID 的方式杀死了 firefox，我注意到需要做三步，首先输入 k，其次输入 PID（default 是排在第一个的进程的 PID），最后输入杀死方式，默认使用 SIGTERM（即输入 15）。有时只需连着两个回车就行。

输入 q 直接退出。

2、jobs ​

解释如图输出：sleep 1000 使得该进程在前台运行，shell 被阻塞；输入 ctrl Z，相当于发送 SIGTSTP 信号，使当前进程由运行状态暂停，shell 收回控制权。

作业是当前 shell 眼中的一些任务，一个作业可能有多个进程。进程是内核眼中的任务。

Jobs 是查看在当前终端中有哪些作业的工具，也就是说它无法输出其他终端启动的进程，也无法输出子进程的作业、自己父进程的作业，更无法像 ps 一样输出 PID，但它可以输出作业状态的具体单词，如 stopped/running 等。在下图的输出中 1 表示作业编号，+ 表示当前作业。类似的还有 -，表示前一个作业。

输入 fg %1 表示对作业 1 移至前台，并向该进程发送 SIGCONT 信号，此时 shell 被阻塞。

再输入 bg %1 表示将作业 1 移至后台，并向该进程发送 SIGCONT 信号，此时 shell 不等待其运行完，因此会立即返回提示符，但我们可以通过 jobs 发现有这样一个进程运行在后台。这里的 & 就代表如此。

对于 jobs 作业，我进一步思考：如下图，创造两个 sleep，就会发现作业编号有了 1 和 2。同时注意 + 和 - 的变化，从创造 sleep 2000 起，2 始终是 +，1 始终是 -，直到 2 被搞到后台去，就变成 1 是 + 2 是 - 了。可见，+ 应该只在 stopped 的作业上。并且，后续我又创造了 4 个 sleep 的进程，两个前台暂停两个后台运行，我发现：当存在 3 个及以上进程且其中有 2 个是 stopped 的时候，剩下的 running 不会标 + 和 -（如上图）。

如下图，输入 sleep 1000 | grep hello &（意味着睡 1000s，睡完后看看输出有没有 hello，在后台进行，显然正常情况下输出不可能有 hello，最后就返回 1 退出了），我又输入 jobs -l，得到下图。由此可见，一个作业（2）是可以有多个进程（4838、4839）的。

3、kill ​

PPID 是父进程 ID，PGID 是进程组 id（group）

Kill PID 对应的信号是 SIGTERM（15），礼貌终止，用 jobs 或 ps 看输出是 terminated；

Kill -9 PID 对应的信号是 SIGKILL（9），强制杀死，用 jobs 或 ps 看输出是 killed。

经过实验，我发现对于一个停止了的 sleep 进程，SIGTERM 不起作用，SIGKILL 可以干死；对于一个在后台运行的 sleep 进程，SIGTERM 可以终止。

Shell job 影不影响需要具体情况具体分析，对于输入为 sleep 3000 | grep hello，如果 kill 了后一个 grep hello，sleep 3000 正常进行；kill 前一个 sleep 3000，grep hello 输出 exit 1，也算半正常进行，只是提早结束了；输入 kill -PGID，就杀掉了整个进程组，就结束了。

4、process group ​

代码运用两次 fork，并对后一次 fork 进行 setpgid（0，0），实现了先创建一个在父进程的进程组内的子进程，再创建一个独立于之前进程组的进程。

具体解释：代码中，先 fork 一个子进程，pgid 与父进程相同；再 fork 一个子进程并执行 setpgid（0，0），setpgid 的原型是 int setpgid(pid_t pid, pid_t pgid)，linux 对两个参数为 0 的时候进行了规定：第一个参数为 0 表示当前进程，第二个参数为 0 表示将第一个参数赋值给第二个参数，所以相当于执行了 setpgid(getpid(), getpid())；此时这个子进程还保持着与父进程的关系（可以看到下图，ppid 依旧是父进程），但 pgid 已经与父进程不同了。

Ctrl C 针对的是当前终端的前台进程组。平时输入命令行的时候，假设我们要 run 一个大程序，在后台运行，这个时候子进程会自己运行 setpgid（0，0）搬到新的进程组，这样即使前台在执行新的子进程的时候按下了 ctrl C，也不会把后台进程也杀掉。

对上图输出，我们会发现无法在程序运行的时候输入，我们可以执行程序的时候加 & 来把程序放在后台运行，然后直接回车没有关系，接着输入上图中的 ps 命令。

5、SIGUSR1 ​

首先解释代码：这个函数是一个回调函数（callback function），大概意思是当某个特定事件发生的时候，操作系统负责调用之前写好的函数。signal(SIGUSR1, handler); 就在 main 函数里告诉 kernel 如果收到 SIGUSR1 的信号就去执行 handler 函数。

这里使用 write 而不用 printf 是因为 write 更信号安全，printf 内部有缓冲区不安全；write 的三个参数分别为 fd 文件描述符，这里的 1 表示 stdout 标准输出，输出在终端屏幕；第二个参数是字符串常量 const char*；第三个参数是要打印的字节数（signal received 正好 16 字节，加上空格和 \0）。

void handler(int sig) {
    write(1, "signal received\n", 16);
}

在具体操作中，我们要打开另一个终端输入，因为目前终端 pause 掉了，所有的输入都没用；我们在另一个终端输入 kill -SIGUSR1 17413，就会看到这个 pause 的终端打印出 signal received，然后依旧 pause，最后我们要用 ctrl C 去结束。

这里用 kill 不代表杀死，而是 linux 的约定，就是发送信号。重复发送信号，每次发送都会出现 signal received。

6、SIGUSR1 blocked ​

首先解释代码：sigset_t 是 linux 里一个表示信号集合的类型，其使用 bit mask 位图来实现。在代码中 sigemptyset(&set); 这一步把所有位变为 0，sigaddset(&set, SIGUSR1); 再把 SIGUSR1 对应的编号变为 1，随后 sigprocmask(SIG_BLOCK, &set, NULL) 这一步把 SIGUSR1 给 block 住。代码后续 block 并 sleep，对于在 block 期间收到的信号，操作系统将 SIGUSR1 在 pending 位图中的那一位从 0 改为 1，一旦 unblock 则立刻发送。

运行时，在 block 的时候在另一个终端输入 kill -SIGUSR1 17832，可以看到没有任何反应，睡醒后立刻输出了两行。

然而，重复发送的信号除了第一个之外都会丢失，因为其操作原理中 0 改成 1，后续也只能不断填 1，无法计数。可以在 sleep 的时候重复发送信号，会发现只输出一次 signal handled。

7、SIGCHLD block 与 nonblock ​

首先解释代码：waitpid(-1, &status, 0) 中，-1 表示任意子进程退出，0 表示默认父进程阻塞，一旦有人死就收，但收完还有人没死就得挂着；改为 WNOHANG（with no hang）表示父进程收完就干别的事情。

SIGCHLD 信号是在子进程 exit 的时候发送的，signal(SIGCHLD, handler); 接收信号从而能让 handler 内部的 waitpid 进行判断。这里的 while 在每次执行的时候都会调用 waitpid 去翻进程表，所以可以保证不通过返回信号而是进程 PID 来清理所有死掉的子进程。

代码实现：通过 fork（）创建了五个子进程并同时对五个子进程进行了随机 sleep，并在随机 1、2、3 秒醒来，然后进行 _exit（否则下一个 fork 就变成孙子进程了），这里的下划线表示底层的一种 exit，强制退出。

分析：blocking 和 unblocking 都很好地做到了五个 child 的 exit 和 reaped，没有一个 zombie。

差异在于 unblocking 涉及的 waitpid 的 WNOHANG 参数保证了当下没有子进程死的时候父进程就可以先出来。

9、signal processing programme ​

对比 signal 和 sigaction 的输出，先说结论：我没发现很大差别。

据资料，应该来说后者会很稳定，但我改了几遍代码做了很多次实验也感觉两者都差不多稳定，稳定可能不能完全从打印出来的结果看。结合实验，具体结论如下：

1、一开始输出较稳定，几秒之后就开始有较大随机性，过半分钟会很混乱。主要体现在（1）子进程输出没有按照 PID，推测是 cpu 调度器的随机性；（2）processing 和 child 的输出有重叠性、滞后性。（3）有时单次输出字符串高达 5-8 个。

2、SIGCHLD 在打印层面会有丢失，但概率较少且随机，可能 50-100 个 child 会丢 1-2 个。

3、handler 执行还是很有可靠性的，没有崩溃，一直在 run。

4、据资料，signal 在历史上很不可靠，但现代 linux 好像把 signal 优化成了 sigaction。

10、信号的自动屏蔽与嵌套 ​

A 单信号 ​

代码在接收到 SIGUSR1 信号后会强制睡眠 5 秒，再处理接下来可能收到的信号。

我在另一个终端中发送单个 SIGUSR1 信号后不再发送，进程成功 enter 和 leave；但我在 5 秒内快速发送 4 个 SIGUSR1 信号，发现进程只能做到两次 enter 和 leave。且只要手速够快，在 5s 内发送非常多，也是两个。

首先，相同信号没有嵌套。因为 kernel 在 SIGUSR1 被阻塞（睡眠）的时候把 SIGUSR1 对应的 pending bitmask 的 0 改成 1，并等待 SIGUSR1 不再阻塞的时候再执行（这也是为什么一定会先 leave 再 enter）；

其次，当前处理中的信号不会被屏蔽，会执行完。

最后，如果在当前处理的信号的同时再发送 1 个，会恰好不被屏蔽；但如果多发送了大于等于 2 个，因为 bitmask 只能不断被改为 1，所以会被吞掉，不会全部保留。

B 多信号 ​

代码允许 SIGUSR1 和 SIGUSR2 两种信号。两者基本相同，SIGUSR1 sleep 5s，SIGUSR2 sleep 1s。

观察得到：

1、当执行 kill -SIGUSR1 后立刻 kill -SIGUSR2，SIGUSR2 会嵌套，立刻执行；

2、leave SIGUSR2 后几乎立刻 leave SIGUSR1，且总是如此，说明 SIGUSR1 被 SIGUSR2 打断了，由于 sleep 被打断后会返回还未执行的秒数，不再继续 sleep，会直接执行下一行，因此可以推断出 SIGUSR1 被打断了；

3、不同信号间允许嵌套，这非常合理，尤其是 kernel 需要处理紧急情况的时候；

4、linux 只会屏蔽当前自己的信号。

11、进程空间隔离与进程间通信 IPC ​

A 父子进程 ​

代码定义了全局变量，赋值为 0，局部变量也是 0；然后创建父进程和子进程，并给子进程全局和局部都加 100，父进程都加 1。

结果发现，对于全局变量也惊人地体现出父子进程的不同。

这是由于父子进程本身拥有不同的虚拟内存（及对应的寄存器）。两者的寄存器里存了不同的值，虽同名变量但实则存储在内存不同部分，因此互不影响。

B 管道实验 ​

分析代码：

1、pipe(fd); 创建了 fd（0）为 read 读端；fd（1）为 write 写端。因为后续 fork 了，所以本质上父子进程都有一套 pipe，即程序中总共有两个 fd（0）和（1）。

2、子进程写入了 hello from child process，其实做了很多铺垫如关掉 fd（0），保证能正常写入 kernel 在 pipe(fd) 开辟的缓冲区里；

3、父进程写入了 [parent received]，同样做了很多铺垫如关掉 fd（1），并且最后把两者拼起来打印出来。

4、这里理论上父子进程先后顺序是随机的，如果先父进程，子进程还没写，那不炸了？据资料，read 读是阻塞的，直到有东西写进来，这很好地保证了"管道"一定能传进来自 child 的东西。

5、据资料，单个 pipe 不支持双向通信。

6、据资料，write 也可能阻塞，显然 pipe 开辟的缓冲区大小是有限的，如果一直不读，塞满了就不能塞了。

父进程 RDONLY 只读

D 信号实现进程间通信 ​

分析代码 kill(getppid(), SIGUSR1); 这一步就是做了类似 kill -SIGUSR1 PID 的事情，ppid 是父进程的 PID。

可以看到子进程想要传递信号必须依赖 kernel 实现。

父进程在 user mode 下接收到通知，依靠 bitmask=1 的情况跳转到 handler 函数去执行。

如 SIGUSR1 这样的信号一般不携带数据，且不适合传输大量信息，原因在前面的实验中也有体现，信号依赖 bitmask，一旦传入多个信号，大部分中间的信号都会丢失。使用 pipe 和 FIFO 更好。

使用 sigqueue 传输整数 ​

c
#include <signal.h>
int sigqueue(pid_t pid, int sig, const union sigval value);

可以看到，三个参数分别是 pid，signal 和要传输的东西。其中 union sigval 在 sigval.h 的定义是

c
union sigval {
    int   sival_int;    // 可以携带一个整数
    void *sival_ptr;    // 也可以携带一个指针
};

具体示例：

c
#include <signal.h>
pid_t parent_pid = getppid();
union sigval mysigdata;
mysigdata.sival_int = 100; // 封包数据：放入一个整数
// 发送 SIGUSR1 信号，并附带 mysigdata 数据
sigqueue(parent_pid, SIGUSR1, mysigdata);
